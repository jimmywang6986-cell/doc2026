# 《复途》技术可行性评估：技术要点、实现难度、手机要求

> 本文所有性能数字均为**实测**，不是引用。测试环境：4 核 Intel Xeon、纯 CPU 无 GPU、mediapipe 1.0.1。
> 可复现脚本在 `prototype/`，完整日志见 `/opt/cursor/artifacts/tech_feasibility_log.txt`。

## 一、技术要点：分五层，难度差别极大

| 层 | 做什么 | 难度 | 决定成败的地方 |
| --- | --- | --- | --- |
| 1 感知 | 摄像头 → 33 个人体关键点 | **低**（现成模型） | 选模型档位与运行时 |
| 2 几何 | 关键点 → 临床关节角度 | **极低**（纯数学） | 无 |
| 3 代偿 | 耸肩、躯干侧倾判定 | **低**（阈值法） | 阈值的临床依据 |
| 4 计数 | 往复动作分期与计数 | **低但有必踩的坑** | 迟滞设计 |
| 5 决策 | 处方边界内自治 + 越界升级 | **编码低，设计高** | 安全判定不能交给大模型 |

### 层 1：姿态估计（实测数据）

MediaPipe Pose Landmarker 有三档模型，实测体积与单帧推理延迟：

| 模型 | 体积 | p50 延迟 | p90 延迟 | 折算 FPS | 关键点 |
| --- | --- | --- | --- | --- | --- |
| lite | **5.8 MB** | 14.0 ms | 14.2 ms | 71.6 | 33 |
| full | **9.4 MB** | 16.1 ms | 16.7 ms | 62.0 | 33 |
| heavy | 30.7 MB | 36.6 ms | 37.2 ms | 27.3 | 33 |

Google 官方给出的 Pixel 3 + TFLite GPU 数字是 lite 20 ms / full 25 ms / heavy 53 ms，与上表同一量级。

**最关键的一条判断：康复动作是慢动作，不需要 30 FPS。** 肩关节外展一次往复要 4–6 秒，10–15 FPS 完全够用于角度采样和代偿判定。这一条直接把硬件门槛拉低了一半以上——所有"姿态估计吃性能"的顾虑，在这个场景里都不成立。

### 层 2：几何解算（几十行，零误差）

关节角度就是三点夹角，向量点积加反余弦：

```python
def angle_3p(a, b, c):        # b 为顶点
    v1 = (a[0]-b[0], a[1]-b[1])
    v2 = (c[0]-b[0], c[1]-b[1])
    cos = (v1[0]*v2[0] + v1[1]*v2[1]) / (hypot(*v1) * hypot(*v2))
    return degrees(acos(clamp(cos, -1, 1)))
```

肩外展角 = 上臂向量与躯干向量的夹角；膝角 = 髋-膝-踝三点夹角。用已知真值的合成骨架回归验证，**误差 0.000°**（见验证日志 D 段）。

**一个重要的工程性质：用归一化坐标算角度，结果与分辨率无关。** 480p 和 1080p 算出的角度完全一样。这意味着不需要高分辨率摄像头，也不需要为不同机型调参。

### 层 3：代偿检测（代码简单，参数才是门槛）

- 耸肩：双肩连线相对水平线的倾角
- 躯干侧倾：肩中点-髋中点连线相对铅垂线的倾角

实测：真值 8° 检出 8.00°（容差 12° 内，不告警）；真值 20° 检出 20.00°（超容差，告警）。

**代码是简单的，难的是阈值从哪来。** 12° 这个数字必须由康复治疗师根据患者情况给定，不能拍脑袋。评委问「12 度这个阈值哪来的」时，答案必须是「治疗师定的，写在处方边界里，每个患者可以不同」——这既是临床要求，也正好是「处方边界」这个设计的合理性来源。

顺带一个真实经历：我实现 `shrug_deg` 时用了 `atan2(dy, dx)`，因为左肩 x 坐标小于右肩，dx 为负，算出的角度是 180° 而不是 0°。**这个 bug 是单元测试抓出来的**，靠肉眼看演示视频是发现不了的——这类符号错误会让代偿检测完全失效但看起来"在工作"。

### 层 4：计数状态机（唯一一个必踩的坑）

用单个角度阈值计数，在关键点抖动下会疯狂误计数。实测对比（真实动作 6 次）：

| 关键点抖动 | 单阈值计数 | 双阈值迟滞计数 |
| --- | --- | --- |
| ±0° | 6 | 6 |
| ±5° | 6 | 6 |
| ±9° | **8** | 6 |
| ±14° | **12** | 6 |

修法很简单：双阈值迟滞（越过 45° 才算抬起，回落到 20° 以下才算完成）加上保持帧数要求。**几行代码的事，但不做的话整个训练数据全是错的**，而且错得不明显——患者做 6 次系统记 12 次，依从性数据直接失去意义。

### 层 5：Agent 决策（本项目真正的技术判断）

最重要的一条工程原则：**安全判定绝不能交给大模型。**

大模型会算错、会被话术带偏、会为了鼓励患者而放宽标准。所以设计成两段：

1. **确定性规则引擎先行**（`safety_gate`）：疼痛超阈、活动度较基线骤降、连续未训练——任一命中即升级，纯规则、无模型参与、理由逐条可追溯。漏报比误报危险得多，所以不做加权平均，命中即触发。
2. **大模型仅在放行后参与**，且输出被处方边界**夹紧**。

实测行为：

| 场景 | 闸门判定 | 大模型能否介入 |
| --- | --- | --- |
| 指标正常 | proceed | 是 |
| 疼痛 NRS 4 | stop_session | 否 |
| 疼痛 NRS 7 | escalate | 否 |
| 活动度较基线降 35% | escalate | 否 |
| 连续 4 天未练 | escalate | 否 |
| 疼痛 8 且 5 天未练 | escalate（列出全部 2 条理由） | 否 |

输出夹紧实测：模型建议「99 次 / 180°」→ 实际下发「20 次 / 90°」；建议「0 次 / 5°」→ 下发「10 次 / 45°」；建议「14 次 / 65°」→ 框内原样通过。闸门升级时，模型输出直接丢弃、不下发任何方案。

这个设计一举拿下三样东西：**合规**（AI 不做医疗判定）、**技术性**（有状态、有约束的真 Agent）、**可解释**（答辩时每个决策都能追到规则和数据）。

## 二、实现难不难：不难，但难点不在代码

### 代码量实测

| 文件 | 代码行数 | 内容 |
| --- | --- | --- |
| `rehab_core.py` | 206 | 角度、代偿、计数状态机、安全闸门、输出夹紧 |
| `test_rehab_core.py` | 225 | 19 个单元测试，全部通过 |
| `e2e_pose.py` | 117 | 端到端：图像 → 关键点 → 角度 → 代偿 → 决策 → 标注图 |
| `bench_pose.py` | 61 | 模型体积与延迟基准 |

**核心算法两百行出头。** 感知层是现成模型不用自己写，几何是纯数学，状态机和规则引擎都是确定性逻辑。这个原型从零到端到端跑通，实际耗时不到一小时。

### 端到端已在真实图像上验证

<img src="/opt/cursor/artifacts/pose_pipeline_verified.jpg" alt="真实图像上的姿态解算与决策链路" />

一张真实人物照片（瑜伽战士式），检出 33 个关键点，解算结果：左肩外展 94.9°、右肩外展 105.2°、左膝 175.1°（后腿伸直）、右膝 107.3°（前腿屈曲）、耸肩 6.0°、躯干侧倾 1.5°，代偿判定正常，安全闸门放行并下发「16 次 / 目标 75°」。所有数值符合该姿势的解剖实际。

### 真正难的三件事，都不是编码

**1. 机位与 2D 投影歧义——最大的工程风险。**

MediaPipe 给的是 2D 投影坐标（虽然也有 z 但精度有限）。手机摆的角度不对，算出的角度就不对。同一个 90° 外展，正面拍是 90°，斜 30° 拍可能算成 75°。

对策：做**机位引导**——屏幕上画人形轮廓框，患者站进框里、姿态置信度达标才允许开始训练；动作只选**在单一平面内完成**的（坐位肩外展、坐位伸膝、坐站转移），避开需要判断前后深度的动作。这也是为什么 MVP 只做 2–3 个动作不是偷懒，是刻意规避已知风险。

**2. 阈值的临床依据。** 代码 5 分钟，参数要治疗师。没有治疗师参与，这个作品在评审时会被认为"技术玩具"。

**3. 真实被试与评测数据。** 这是资源问题不是技术问题，也是三天里最可能卡住的一环。

## 三、对手机的要求：低，但有一个必须避开的坑

| 项 | 要求 | 说明 |
| --- | --- | --- |
| 存储 | 模型 5.8 MB（lite），整包 20–30 MB | 比大多数 App 小 |
| 内存 | 3 GB 及以上舒适，2 GB 可行 | lite 档位很轻 |
| 算力 | 中低端 4 核 Android 即可 | 需求只要 10–15 FPS，原生 GPU delegate 能到 20–30 |
| 摄像头 | **720p 足够** | 角度用归一化坐标，与分辨率无关 |
| 网络 | **可完全离线** | 姿态估计端侧运行；只有 Agent 决策需联网，可缓存降级 |
| 系统 | Android 8+ / iOS 13+ | MediaPipe Tasks 覆盖范围 |

### 必须避开的坑：不要做浏览器方案

我此前建议「用 Web 开发最快」，**这条要修正**。实测数据与公开基准都指向同一个结论：

- BlazePose 在 **Pixel 5 浏览器**里只有 **11–12 FPS**（lite/full），heavy 只有 5 FPS
- 同样模型的**原生 Android** 运行时是 22–32 FPS

浏览器方案在中低端安卓机上会掉到个位数帧率，演示时必翻车，而复评可能有「场景模拟演示」环节。

**两条正确的路：**

1. **原生 Android + MediaPipe Tasks**（推荐用于最终交付）。性能最好，也符合原文「可安装/运行」的要求。
2. 如果因为时间必须走 Web，**把模型换成 MoveNet Lightning**——17 个关键点（COCO），浏览器里 Pixel 5 能到 34 FPS。而本方案只需要肩、肘、腕、髋、膝、踝，**17 点完全够用**，33 点是浪费。

### 三天时间下的现实路径

先用 Python 桌面版把算法和演示跑通（就是 `prototype/` 里这套，已经能跑），保证演示视频拍得出来；同时套一个最小 Android 壳保证「可安装/运行」的交付要求。不要在三天里追求一个完美的原生 App。

## 四、复现方式

```bash
pip install mediapipe opencv-python-headless pytest
# 无头环境还需: sudo apt-get install -y libegl1 libgles2 libgl1

# 下载模型
for m in lite full heavy; do
  curl -sSL -o pose_landmarker_$m.task \
    "https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_$m/float16/latest/pose_landmarker_$m.task"
done

cd prototype
python3 -m pytest test_rehab_core.py -q   # 19 个单元测试
python3 test_rehab_core.py                # 逐项验证报告
python3 bench_pose.py                     # 模型体积与延迟
python3 e2e_pose.py <图片路径>             # 端到端 + 标注图
```
