# 作品 2｜赛道三 · 智能体创新

## 作品名称

**《实训安全与故障排查智能体 —— 面向职业院校实训场景的 RAG + 工单 Agent》**

（备选命名：《扫码即问 · 排障有据：实训设备智能助手》）

- 归口推荐主题：**数智转型 · 行业增效**（兼「数智伴学 · 教育助教」）
- 建议报名组别：**学生组**（评审要点为「创意独特性、技术学习与应用能力、成长潜力」，最适合展示技术实现），教师任指导教师
- 若由教师主导，改报教师组，叙事重心调整为「实训教学中的知识沉淀与安全管理」

## 一、为什么选这个题

赛道三技术性 25% + 创新性 25% 占了一半，评的是「技术实现难度、系统架构合理性、代码/配置质量」。这个题目能同时踩中四个技术点，且每一个都能在架构图上画出来：

1. **RAG 检索增强**——设备手册、操作规程、历史故障单构成私域知识库，通用大模型答不了的问题它能答
2. **工具调用**——不止回答，还能落地动作（生成维修工单、写回台账、通知责任人）
3. **工作流编排**——现象识别 → 分级判断 → 分步处置 → 安全禁令 → 工单/转人工，是有状态的多步流程，不是单轮问答
4. **上下文注入**——扫设备二维码进入对话，Agent 一开口就知道是哪台设备、什么型号、有什么历史故障

同时它避开了纯技术炫技的陷阱：实用性 20% 有真实使用者（实训学生和指导老师），复评「场景模拟演示」时可以当场扫码提问。

## 二、系统设计

### 用户旅程

```
学生在实训中遇到设备报错
   │ 扫设备二维码（与作品 1 共用同一套码，但进入的是不同应用）
   ▼
Agent 已知上下文：设备编号、型号、所在实训室、历史故障记录
   │ 学生用自然语言描述现象（"E07 报警，主轴不转"）
   ▼
┌─ 意图与现象识别（结构化抽取：报错码 / 部位 / 现象 / 是否带电）
├─ 安全前置判断 ──► 命中高危 → 立即输出停机与断电指令，禁止继续操作
├─ RAG 检索（设备手册 + 操作规程 + 历史故障单，混合检索 + 重排）
├─ 分级决策 ──► A 学生可自行处置 / B 须指导教师在场 / C 必须报修
├─ 输出分步处置方案（每步带安全提示与判断依据出处）
└─ 工具调用 ──► 生成维修工单 / 写回设备台账 / 推送责任人
   │
   ▼
知识库无法覆盖 → 明确拒答 + 转人工 + 记录该问题进待补充清单
```

### 三个设计决策（这是创新性 25% 的落点）

1. **分级授权而非一律作答。** 通用 AI 助手最大的问题是对着高压设备也敢教人动手。本作品把「能不能自己修」作为一等公民输出：A/B/C 三级授权，C 级直接不给操作步骤，只给报修。这在实训安全场景是真实需求，也是同类作品几乎不会做的设计。
2. **强制引用出处。** 每一步处置都标注来自手册第几节或哪条历史故障单。既提升可信度，也让答辩时经得起追问。
3. **拒答与知识回流。** 检索置信度不足时不硬编答案，转人工并把问题写入「知识库待补充清单」，形成自我完善闭环。这条把作品从「一次性 demo」变成「可运营的系统」，对准完整性 20%。

### 技术路线（两条都合规，按团队能力选）

**路线 A：编程实现（技术性得分更高，需提交核心源代码）**

| 层 | 选型 |
| --- | --- |
| 前端 | 极简 Web（移动端优先），扫码带 `device_id` 参数进入 |
| 服务 | Python + FastAPI |
| 检索 | 向量库（Chroma / FAISS）+ BM25 混合检索 + 重排 |
| 模型 | 通用大模型 API（可对接国产模型，答辩时更稳妥） |
| 编排 | 自写状态机或 LangGraph 类框架，节点即上图各步骤 |
| 工具 | 工单生成、台账写回、消息推送（可对接作品 1 的多维表格 API，形成数据闭环） |
| 存储 | SQLite（工单、会话、待补充清单） |
| 交付 | Docker Compose 一键启动 + `.env.example` + 完整配置说明 |

**路线 B：低代码实现（4 天更保险，需提交平台导出文件或完整配置截图）**

在 Coze / 文心智能体 / 讯飞星火 / 钉钉 AI 助理 等平台搭建：知识库上传手册与故障单 → 工作流编排上述节点 → 插件调用生成工单 → 发布为可访问链接与测试账号。

**建议**：**主体走路线 B 保证按时可运行，同时把关键的检索与分级逻辑用路线 A 的方式实现一个可跑的核心模块并提交源码**。这样既有「可运行、可现场演示」，又有「代码质量」可评。原文明确支持低代码与编程两种开发方式，两者材料要求不同但都认可。

## 三、必须交付的技术文档三件套（原文硬性列举）

1. **系统架构图**——把上面的流程图画成正式架构图，分层标出前端、编排层、检索层、模型层、工具层、存储层与外部依赖
2. **核心逻辑说明**——分级授权规则表、检索策略（分块大小、召回数量、重排逻辑、置信度阈值）、拒答条件
3. **提示词（Prompt）设计**——这一项建议成体系地写，而不是贴几段文字：

| Prompt 模块 | 作用 |
| --- | --- |
| 角色与边界 | 身份设定、能力范围、绝不越界的事项 |
| 安全约束 | 高危操作黑名单、必须停机断电的触发条件、免责声明 |
| 检索结果注入模板 | 如何把召回片段与出处一起送入上下文 |
| 结构化输出 Schema | 强制 JSON 输出（授权等级 / 步骤数组 / 引用来源 / 是否开工单） |
| 拒答策略 | 置信度不足或超范围时的固定话术与转人工动作 |
| 少样本示例 | 3–5 个真实故障问答对，稳定输出格式 |

准备 **30 条真实问题**（从历史故障单和实训老师那里收集），跑三组对比：

| 指标 | 通用大模型直接问 | 本智能体 | 说明 |

| 引用可核查率 | 0% | ___% | 能否指到手册具体位置 |
| 高危场景正确拦截率 | ___% | ___% | 10 条高危问题中拦住几条 |

这张表的杀伤力在于：它证明了「为什么需要专门做一个智能体，而不是直接用通用大模型」——这是评委必然会问的问题，也是答辩时最关键的一击。

## 七、答辩与现场演示准备（复评可能考）

原文写明复评「视情况进行线下答辩、场景模拟演示」，且有企业技术专家参与。准备三件事：

1. **离线可跑包**——不依赖学校内网、不依赖单一外部服务；准备本地模型或备用 API key，网络挂了也能演示
2. **备用录屏**——现场翻车时立刻切录屏，别让空白时间发生
3. **预判问题的答案**：
   - 「和直接用 ChatGPT/文心有什么区别？」→ 甩出评测对比表 + 私域知识库 + 分级授权
   - 「答错了怎么办、出安全事故谁负责？」→ 讲拒答策略、C 级不给操作步骤、免责设计、人工兜底
   - 「数据从哪来、有没有侵权？」→ 说明手册来源与授权、脱敏处理
   - 「能推广到别的学校/企业吗？」→ 知识库可替换、配置化的设备档案、迁移成本说明
